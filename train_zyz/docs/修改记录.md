### 核心发现：为什么 OOM 不触发而 NCCL 死锁一定触发

三人分别确认了一个关键事实——日常 OOM 终止（90%+ 的失败）走的是安全路径：

- **Python OOM**：`torch.OutOfMemoryError` → Python 栈展开 → `cuCtxDestroy` 正常 → GPU 安全
- **NCCL 死锁**：GPU 连续 active 600s → SIGABRT 100% 命中 → 5 GPU 同时异常退出 → 驱动全局状态损坏

这解释了为什么问题隐藏极深——最常见的失败模式恰好绕过了驱动 bug。

## 2026-05-15 (v18)：NCCL PXB 回退 + GPU 状态恢复

### 问题

1. **NCCL ALLGATHER 完全卡死**：v17 的 `NCCL_P2P_LEVEL=PXB` + `NCCL_ALGO=Tree` 在 A100 PCIe 上导致首次 FSDP ALLGATHER 600s timeout（所有 5 rank 同时 timeout），比 v16 的 NVL（慢但能跑 130s/step）更差。根因：ACS/IOMMU 阻止 PCIe P2P。
2. **GPU 状态损坏**：NCCL 崩溃（SIGABRT -6）后 `torch.cuda.device_count()==0`（`CUDA unknown error`），`/dev/nvidia*` 被僵尸进程持有。
3. **GPU 检测不可靠**：`torch.cuda.device_count()` 可能返回 5 但 CUDA context 创建失败（`is_available()=False`），导致 torchrun 启动后所有 worker 报 `ProcessGroupNCCL: no GPUs found`。
4. **GSP-RM Firmware 禁用**：`NVreg_EnableGpuFirmware=0` → GPU 状态由 host driver 软件管理，崩溃后恢复慢（20-30s vs 正常 5-10s）

### 修改

**blueprints/OpenFundus_SFT_zyz.magnus + LoRA_zyz.magnus**:
- NCCL: 移除 `P2P_LEVEL=PXB` + `SOCKET_IFNAME` 过滤 + 实验性微调，`ALGO=Ring`
- Shell 重试前 GPU 清理：`fuser -k /dev/nvidia* /dev/nvidiactl` + `sleep 15`
- GPU 检测：逐卡验证 CUDA context（`torch.zeros(1, device='cuda')`），替代不可靠的 `device_count()`
- GSP-RM 自适应：检测 `nvidia-smi -q | grep GSP`，禁用时 sleep 从 10s 延长至 25s

**skill 文件**:
- sft_blueprint.skill: 重写 NCCL 拓扑适配为 v18 + GPU 检测验证
- sft_issues.skill: 重写 A100 PCIe NCCL 排错 + GPU 状态损坏 + CUDA 初始化失败诊断
- SFT.skill: 更新 NCCL 通讯优化 + 已知问题表
- README.skill: 更新全局已知问题 + FSDP 节

### v18 补充修复 (同日)：device_count() 不可靠导致 CPU fallback 后仍尝试 NCCL 初始化

**问题**：蓝图 GPU 检测正确识别 0 张可用 GPU → `LAUNCHER=python3`，但 `sft_train.py` 中 `n_gpu = torch.cuda.device_count()` 返回 5（驱动级别查询）→ `n_gpu > 1` 为 True → 调用 `dist.init_process_group(backend="nccl")` → 报错 `RANK expected, but not set`（python3 启动无分布式环境变量）。同时 Magnus 注入的 `CUDA_VISIBLE_DEVICES=0,1,2,3,4` 未清理，导致 `device_count()` 持续返回 5。

**修改**:
- `sft_train.py`: `n_gpu = torch.cuda.device_count() if torch.cuda.is_available() else 0`
- `sft_train.py`: GPU 显示行增加 `n_gpu=0` 时的 CPU fallback 提示
- 两个 `.magnus` 蓝图: CPU fallback 时 `unset CUDA_VISIBLE_DEVICES`
- `sft_issues.skill`: 新增 device_count() vs is_available() 不一致排错
- `sft_blueprint.skill`: 新增 CPU fallback 时清理 CUDA_VISIBLE_DEVICES 文档

## 2026-05-15 (v17)：NCCL PCIe 修复 + 优化器 OOM 防护

### 问题

1. **训练极慢（117s/step）**：蓝图 `NCCL_P2P_LEVEL=NVL` 在 A100 PCIe（无 NVLink）上导致 NCCL 回退到 CPU/socket 通信，5 卡 FSDP all-gather 带宽骤降
2. **Step 8 OOM 无限循环**：grad_accum=8 边界首次 optimizer.step() 集中分配 CUDA buffer 导致显存溢出，无 checkpoint 导致 shell 重试从 step 1 重新开始，循环 OOM

### 修改

**blueprints/OpenFundus_SFT_zyz.magnus + LoRA_zyz.magnus**:
- `NCCL_P2P_LEVEL=NVL` → `PXB`（适配 A100 PCIe）
- `NCCL_ALGO=Ring` → `Tree`（PCIe 拓扑更稳定）

**sft_train.py**:
- 训练循环前预分配优化器 CUDA buffer（`optimizer.step()` + `optimizer.zero_grad()`），避免首次 optimizer step 集中分配
- optimizer step 前 `torch.cuda.empty_cache()` 碎片整理
- optimizer step 内 try/except 捕获 CUDA OOM：跳过此累积周期，清空梯度继续训练（不再崩溃重试）

## 2026-05-13 (v13)：显存 / 通讯 / 性能指标全面优化

### 背景

针对 Qwen-2.5-72B 在 80GB A100 上训练，目标：
1. 降低 GPU 显存占用，力争 72B 从 3 卡降到 2 卡
2. 优化 FSDP NCCL 通讯效率
3. 加入全面性能诊断指标（每步耗时分解、显存结构分解、分卡查看）

### 修改

**Phase 1 — FSDP CPU Offload（核心显存优化）**

- `sft_train.py` 新增 `--cpu_offload`（默认 False）：`CPUOffload(offload_params=False)` 将 AdamW 优化器状态（momentum+variance, fp32）移至 CPU RAM
- `sft_train.py` 新增 `--backward_prefetch`（默认 "pre"）：FSDP `BackwardPrefetch.BACKWARD_POST` 延迟预取，进一步节省显存
- `sft_train.py` 新增 `--fused_optimizer`（默认 True）：`AdamW(fused=True)` 单 CUDA kernel 优化器 step，5-10% 加速
- 显存分析：72B FULL_SHARD 所需显存从 ~1152/N GB 降至 ~288/N GB（CPU offload 开启时）
- 蓝图新增 `CpuOffload`（bool）和 `BackwardPrefetch`（Literal["pre","post"]）参数
- `submit_sft.py` 新增 `CPU_OFFLOAD` 和 `BWD_PREFETCH` 配置项

**Phase 2 — NCCL 通讯优化**

- `sft_train.py` Python 层：`NCCL_ALGO=Ring`、`NCCL_PROTO=Simple`、`NCCL_MIN_NCHANNELS=4`
- 蓝图 shell 层：追加 `NCCL_NSOCKS_PERTHREAD=4`、`NCCL_SOCKET_NTHREADS=2`
- LoRA 蓝图同步 NCCL 环境变量

**Phase 3 — DataLoader 优化**

- `prefetch_factor=4`、`persistent_workers=(num_workers > 0)` — 减少 worker 重启开销
- 诊断频率降低：step 进度 10→50、内存诊断 40→100、慢步阈值 30s→20s

**Phase 4 — 全面性能指标系统**

- **CUDATimer** 类：基于 `torch.cuda.Event(enable_timing=True)` 精确 GPU 计时
  - 指标：`perf.forward_ms`、`perf.backward_ms`、`perf.optimizer_ms`、`perf.comm_ms`、`perf.total_ms`、`perf.tokens_per_sec`
  - 写入频率：每 `perf_metric_steps`（默认 50）step，仅 rank 0
- **get_memory_breakdown(device_id)**：`allocated_gb`、`reserved_gb`、`peak_allocated_gb`、`fragmentation_pct`
  - 写入频率：每 `memory_metric_steps`（默认 20）step，**所有 rank**（带 `labels={"rank": "N"}` 支持 Magnus 面板分卡过滤）
- **estimate_memory_components(model, n_gpu)**：step=0 打印理论显存估算（参数/优化器/梯度/合计）
- 新增 CLI：`--perf_metric_steps`（默认 50）、`--memory_metric_steps`（默认 20）

### 效果

- Magnus 面板可按 GPU 分别查看显存占用，快速定位显存瓶颈

## 2026-05-06 (v10)：run_generation_eval NCCL 超时修复 — barrier 同步防止 rank 脱节

### 问题

训练日志中出现 NCCL `_ALLGATHER_BASE` 超时（600s），发生在 step=0 的初始生成式评估（`[推理-initial]`）期间。崩溃链：

```
run_generation_eval() 被调用
  → rank 1: if local_rank != 0 → return（立即退出函数）
  → rank 1: 进入训练循环 → FSDP forward → _ALLGATHER_BASE 等待 rank 0
  → rank 0: 仍在 run_generation_eval() 中逐样本生成（~10 min / 101 条）
  → rank 0: 不参与训练循环的 collective
  → 600s 后 watchdog 杀 rank 1 → SIGABRT
```

根本原因：`run_generation_eval()` 中 `if local_rank != 0: return` 让非 rank 0 进程在 state dict 收集（NCCL collective）之前就返回，然后立即进入训练循环发送需要 rank 0 参与的 FSDP allgather。但 rank 0 还在生成文本（~10 分钟），无人参与该 collective。

### 修改

**sft_train.py** `run_generation_eval()` 重构同步流程：

1. **State dict 收集移到 `local_rank` 检查之前**：所有 rank 参与 `model.state_dict()` 的 NCCL collective
2. **barrier 1**：state dict 收集后同步，确保 NCCL 操作全部完成
3. **非 rank 0 等待 barrier 2**：阻止非 rank 0 进程立即返回训练循环
4. **barrier 2**：rank 0 推理完成后通知所有 rank，同步返回训练循环

```python
# 旧：rank 1 立即返回 → 进入训练循环 → NCCL 超时
if local_rank != 0:
    return

# 新：所有 rank 先参与 state dict collective，barrier 同步后再分流
_state = model.state_dict()        # all ranks
dist.barrier()                     # sync after collective
if local_rank != 0:
    dist.barrier()                 # wait for rank 0 to finish generation
    return
# ... rank 0 generates ...
dist.barrier()                     # signal completion
```

### 效果

- 生成式评估期间不再有 NCCL 超时
- 所有 rank 在推理完成后同步进入训练循环
- FSDP forward 的 allgather 始终有全部 rank 参与

### 修改文件

- `train/sft_train.py` — `run_generation_eval()` 重构 barrier 同步
- `PHY-LLM-Basic-Algorithm/sft_train.py` — 同步副本

## 2026-05-06 (v11)：SFT 性能优化 — 硬件加速 + 7B/72B 差异化 + NCCL 修复

### 修改

**sft_train.py** 全局优化：

1. **A100 硬件加速**
   - `torch.set_float32_matmul_precision('high')` — TF32 tensor core
   - `torch.backends.cudnn.benchmark = True` — 固定 shape 自寻最优算法
   - `config.attn_implementation = "flash_attention_2"` — 显存节省 30%+，推理/训练加速（需 flash_attn 已安装；无则 fallback sdpa）

2. **NCCL 单节点优化**
   - `NCCL_P2P_LEVEL=NVL` + `NCCL_P2P_DISABLE=0` — 撤销蓝图的 P2P_DISABLE，走 NVLink 直连（同节点双 A100）

   - `warnings.filterwarnings` 过滤 `torch.distributed.fsdp` 的 FutureWarning
   - **不迁移到 DCP `get_state_dict`**：新 API 不支持 `rank0_only`，72B 模型会导致每 rank 各持一份完整 CPU state dict（~144GB × N），必然 OOM

4. **7B/72B 自动差异化配置**
   - `is_large_model = total_params > 30`（>30B → 大模型模式）
   - 7B：跳过 `gradient_checkpointing_enable()`，显存充足无需以时间换空间
   - 72B：保持开启 `gradient_checkpointing_enable()`，显存安全优先

5. **训练前初始评估轻量化**
   - 注释 `run_generation_eval(tag="initial")` — 训练前生成式评估耗时 10+ 分钟，收益有限
   - step=0 loss 评估保留（train_loss + eval_loss），提供训练前 baseline
   - checkpoint 评估 + final 评估完整保留，训练全周期质量变化仍可追踪

6. **DataLoader 多线程 + 锁页内存**
   - `num_workers: 0 → 2`，`pin_memory=True`，`prefetch_factor=2`
   - CPU→GPU 传输加速，tokenization 并行化

**submit_sft.py** 默认值修正：
- `MAX_LENGTH: 4096 → 1024` — 与 sft_train.py argparse default 一致，防止序列长度意外翻倍导致显存暴涨

### 拒绝的 AI 建议

- **`torch.compile`**：与 FSDP 兼容性不稳定，可能引入 hang/OOM，暂不启用
- **DCP `get_state_dict` 迁移**：新 API 不支持 `rank0_only`，72B 模型每 rank 各持 ~144GB CPU state dict，必然 OOM
- **`NCCL_TIMEOUT` 环境变量**：NCCL 无此环境变量，无效
- **`init_process_group(timeout=7200)`**：根因已由 v10 barrier 修复，无需延长超时

## 2026-05-04 (v3)：Checkpoint 损坏恢复修复 — 原子保存 + 损坏检测 + 最终兜底

### 问题

训练中途被杀（OOM / NCCL 超时 / 节点抢占）导致 checkpoint 保存不完整，重试时 `_load_safetensors_state` 因 `SafetensorError` 崩溃，且无 try/except 兜底。Shell retry 每次恢复同一损坏 checkpoint，确定性失败。3 次重试耗尽后直接退出，没有从头开始的选项。

崩溃链：
```
训练被杀 → save_pretrained 写到一半
  → checkpoint-latest/model.safetensors 截断
    → 重试时 _load_safetensors_state 抛异常
      → Step 4 无 try/except → 崩溃
        → Shell retry 恢复同一损坏 checkpoint × 3
          → FATAL 退出
```

### 修改

**两个蓝图** `OpenFundus_SFT_zyz.magnus` 和 `LoRA_zyz.magnus`：

#### 问题 A — 原子保存（防损坏产生）
```python
# 旧：直接写 checkpoint-latest，中途被杀 → 截断
m.save_pretrained("checkpoint-latest", state_dict=state)

# 新：写临时目录 → os.rename 原子覆盖
tmp_path = f".ckpt-tmp-{step}"
m.save_pretrained(tmp_path, state_dict=state)
os.rename(tmp_path, "checkpoint-latest")   # 原子操作
```
被杀时 `.ckpt-tmp-XXX` 损坏不影响已有 checkpoint。

#### 问题 B — 加载容错（损坏时优雅降级）
```python
# 旧：直接 load_file，损坏文件抛 SafetensorError → 进程崩溃
state = load_file(single_path)

# 新：try/except 包裹，返回 None
try:
    state = load_file(single_path)
except Exception as e:
    log(f"checkpoint 损坏: {e}")
    return None

# Step 4：try/except 包裹，None 时从头训练
try:
    state = _load_safetensors_state(ckpt)
    if state and len(state) > 0:
        model.load_state_dict(state, strict=False)
    else:
        log("无有效权重，从头开始训练")
except Exception as e:
    log(f"加载失败: {e}，从头开始训练")
```

#### 问题 C — Shell 最终兜底（防确定性失败）
```bash
# 3 次重试耗尽后 → 清理损坏 checkpoint → 再尝试最后一次
if [ $TRAIN_OK -eq 0 ]; then
    rm -rf "{output_dir}/checkpoint-latest"
    torchrun ... --resume_from_checkpoint "" ...
fi
```

### 效果
- 原子保存消除 checkpoint 损坏的主要来源
- Python 层容错让单次损坏不会导致进程崩溃
- Shell 最终兜底确保即使所有重试失败也不会直接退出

### 修改文件
- `OpenFundus_SFT_zyz.magnus` — `save_checkpoint`、`_load_safetensors_state`、Step 4 resume、shell retry
- `LoRA_zyz.magnus` — `save_lora_checkpoint`、`_load_safetensors_state`、shell retry
- `SFT.md` §8.13 — 新增 checkpoint 损坏处理文档

## 2026-05-03 (v2)：NaN loss 处理修复 — float32 loss + 计算图安全的 NaN 跳过

### 问题

训练到 step ~110 时产生 NaN loss，NaN 处理代码用 `torch.zeros_like(loss)` 替换损失，但该操作破坏了计算图（`zeros_like` 返回叶子张量，无 `grad_fn`），导致 `backward()` 失败。由于 FSDP 依赖 backward hook 触发 NCCL REDUCE_SCATTER 同步，backward 失败后 NCCL collective 卡死，10 分钟后 watchdog 杀进程。

崩溃链：
```
样本产生 NaN loss
  → zeros_like(loss) 返回叶子张量，无 grad_fn
    → backward() 报 "does not require grad"
      → FSDP 的 REDUCE_SCATTER 未执行
        → 后续 ALLGATHER/REDUCE_SCATTER 死等前面的完成
          → NCCL watchdog 10min 超时 → SIGABRT
```

### 修改

**两个蓝图** `OpenFundus_SFT_zyz.magnus` 和 `LoRA_zyz.magnus` 的训练循环：

#### 问题 A — float32 loss 计算（防 NaN 产生）
```python
# 旧：bfloat16 下 HuggingFace 内部 loss，大词表(151k)数值下溢出
outputs = model(input_ids=input_ids, attention_mask=attn_mask, labels=labels)
loss = outputs.loss

# 新：手动 float32 cross_entropy
outputs = model(input_ids=input_ids, attention_mask=attn_mask)
logits = outputs.logits
shift_logits = logits[..., :-1, :].contiguous().float()   # ← 关键：转 float32
shift_labels = labels[..., 1:].contiguous()
loss = F.cross_entropy(shift_logits.view(-1, logits.size(-1)), shift_labels.view(-1), ignore_index=-100)
```

#### 问题 B — 计算图安全的 NaN 跳过（防 NCCL 死锁）
```python
# 旧：zeros_like 破坏计算图 → backward 失败 → NCCL 死锁
loss = torch.zeros_like(loss)          # leaf tensor, no grad_fn
try:
    (loss / accum).backward()          # 必然失败
except:
    (torch.zeros(1) / accum).backward()  # 也失败

# 新：torch.where 保留计算图连接 → FSDP hook 正常触发 → NCCL sync 正常
loss = torch.where(
    torch.isnan(loss) | torch.isinf(loss),
    torch.zeros_like(loss),    # 值=0，此处梯度被截断
    loss,                       # 值不变，梯度正常流通
)
(loss / accum).backward()       # 始终成功
```

### 效果
- 即使 loss 是 NaN/Inf，backward 梯度为 0 且 FSDP NCCL sync 正常完成
- 不会再有「NaN → backward 失败 → NCCL 死锁」的连锁崩溃
- 实际训练精度不受影响（NaN step 梯度为 0，等价于跳过该样本）

- `SFT.md` §8.11/8.12 — 重写为 v2 修复描述（float32 + torch.where）
- `LoRA.md` §6.7/6.8 — 同步更新为 v2 方案
