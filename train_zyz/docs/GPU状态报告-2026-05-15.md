### 关键区分

**17:06 的 OOM 没有损坏 GPU。** 这是正常的 Python `torch.OutOfMemoryError` 异常，进程干净退出，CUDA context 被正确释放。nvidia-smi 显示 `No running processes found` 印证了这一点。

**18:04 的 SIGABRT 才是根因。** NCCL watchdog 用信号 6 暴力杀进程，跳过了所有正常清理流程。两种退出方式的本质区别：

| | Python OOM (17:06) | NCCL SIGABRT (18:04) |
|---|---|---|
| 触发条件 | 8-bit Adam state buffer 分配失败 | NCCL ALLGATHER 600s 超时 |
| 退出方式 | Python 抛异常，栈展开，CUDA 资源正确释放 | OS 直接发 SIGABRT，进程瞬间终止 |
| GPU 状态 | **完好** | **损坏** |
| `/dev/nvidia*` | 正常释放 | 被僵尸文件描述符持有 |

## 二、根因与责任归属

### 唯一根因：v17 蓝图的 NCCL 配置

```bash
export NCCL_P2P_LEVEL=PXB        # 强制 PCIe Bridge P2P
export NCCL_ALGO=Tree            # Tree 算法
```

**`PXB` 的含义**：强制 NCCL 使用 PCIe Bridge Peer-to-Peer 通信，绕过 CPU/RAM。这要求节点 BIOS/UEFI 中 ACS (Access Control Services) 和 IOMMU 允许 GPU 之间的 PCIe 直连。该节点的 ACS/IOMMU **阻止了这种直连**，导致 ALLGATHER（约 5GB 数据 × 5 rank = 25GB 的总通讯量）完全无法完成，600 秒后超时。

**对比验证**：

| 版本 | P2P_LEVEL | ALGO | 结果 | 证据 |
|------|-----------|------|------|------|
| v16 | `NVL` (强制 NVLink) | Ring | ~117s/step，能跑完 8 步直到 OOM | 17:06 日志 |
| v17 | `PXB` (强制 PCIe P2P) | Tree | **0 step 完成，直接卡死** | 18:04 日志 |
| v18 | **不设** (让 NCCL 自选) | Ring | 预期正常 2-5s/step | — |

### 责任归属

| 主体 | 是否有责 | 说明 |
|------|---------|------|
| **v17 蓝图 NCCL 配置** | **是 — 直接原因** | `P2P_LEVEL=PXB` 在 ACS/IOMMU 启用的节点上是已知高危设置，NCCL 官方文档明确建议不强制 P2P_LEVEL |
| GPU 硬件 | **否** | 5 张 A100 硬件正常，nvidia-smi 无 ECC 错误，温度正常，17:06 训练正常 |
| NVIDIA 驱动 | **否** | 驱动 550.163.01 工作正常，GSP-RM 禁用是节点配置选择，非故障 |
| Magnus 平台 | **否** | 平台正确分配了 GPU、挂载了存储、注入了环境变量。容器内无 root 是正常安全限制 |

### 为什么容器内无法自行恢复

容器内的 GPU 恢复手段有且只有：
1. `fuser -k /dev/nvidia*` — 杀掉持有 GPU 设备文件的用户态进程
2. `sleep N` — 等待驱动自行恢复

**这两种手段均无效**，因为 GPU 状态损坏发生在 **NVIDIA 内核驱动层**，不在用户态进程层面。恢复 GPU 需要**内核驱动级别的重置**，只有以下方式可行：

| 操作 | 所需权限 | 容器内可用 |
|------|---------|-----------|
| `nvidia-smi -r` (GPU 硬件重置) | root（主机） | 否 |
| `rmmod nvidia && modprobe nvidia` (重载驱动) | root（主机） | 否 |
| 节点重启 | root（主机） | 否 |
| `fuser -k /dev/nvidia*` | 容器内可执行 | 是，但**无效** |

## 四、建议的恢复操作

### 方案 A（推荐）：主机端 GPU 硬件重置

在**宿主机**上以 root 执行，**仅需一条命令，几秒钟**：

```bash
nvidia-smi -r
```

若需逐卡重置：

```bash
nvidia-smi -i 0 -r && nvidia-smi -i 1 -r && nvidia-smi -i 2 -r && nvidia-smi -i 3 -r && nvidia-smi -i 4 -r
```

验证恢复：

```bash
python3 -c "
import torch
print(f'device_count: {torch.cuda.device_count()}')
print(f'is_available: {torch.cuda.is_available()}')
for i in range(torch.cuda.device_count()):
    with torch.cuda.device(i):
        t = torch.zeros(1, device='cuda')
    print(f'GPU {i}: OK')
print('All GPUs recovered.')
"
```

### 方案 B（备选）：重启节点

如果 `nvidia-smi -r` 不可用或无效。

### 方案 C（长期建议）：评估是否启用 GSP-RM Firmware

当前 `NVreg_EnableGpuFirmware=0` 导致 GPU 状态完全由 host driver 软件管理，崩溃后恢复慢（20-30s vs 正常 5-10s），且对 SIGABRT 类异常的耐受性更差。

```bash
# 检查当前设置
cat /proc/driver/nvidia/params | grep GpuFirmware
grep -r "EnableGpuFirmware" /etc/modprobe.d/ 2>/dev/null
```

如无特殊原因（如兼容性需求），建议移除该参数以启用 GSP-RM firmware。

## 六、补充确认（2026-05-15 21:00）

### 节点实际 GPU 数量：6×A100

通过 `tools/diag_gpu.py` 诊断确认，节点实际为 **6×A100 80GB PCIe**（非之前报告的 5 张）。之前蓝图 `gpu_count=5` 请求的是 5 张，SLURM 分配了 GPU 0-4。

### PCIe 拓扑确认

```
NUMA 0: GPU 0,1  (PIX — 同一 PCIe bridge)
NUMA 1: GPU 2,3,4,5  (PIX — 同一 PCIe bridge)
跨 NUMA: SYS (经过 SMP/QPI interconnect)
```

这直接验证了 v17 `NCCL_P2P_LEVEL=PXB` 导致死锁的原因：PXB 要求跨 GPU 通过 PCIe bridge 直连，但跨 NUMA 的 GPU 之间没有 PXB 路径（只有 SYS）。Tree 算法依赖根节点连通所有叶子，跨 NUMA 链路阻断导致整棵树死锁。

### GPU 已恢复正常

管理员执行 `nvidia-smi -r` 后，6 张 GPU 全部通过 7 层诊断验证（CUDA context + tensor + NCCL all_reduce 均正常）。

### 残留风险

GSP-RM firmware 仍然禁用（`EnableGpuFirmware: 0`），同类 SIGABRT 场景的 GPU 损坏风险仍然存在。建议在非容器环境中持续监控 GPU 状态，或评估启用 GSP。
