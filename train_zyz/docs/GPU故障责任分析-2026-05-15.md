# GPU 故障责任分层分析 — 5×A100 80GB PCIe

**日期**: 2026-05-15
**问题**: 一次训练配置错误导致 5 张 A100 GPU 全部不可用，需要管理员介入执行 `nvidia-smi -r`
**核心追问**: 为什么一个容器内的用户代码错误，能导致整节点 GPU 不可用？是谁的锅？

---

## 结论先行

**这不是"谁错了"的单选题，而是五层技术栈叠加的级联故障。** 每一层单独看都有解释，但叠加在一起产生了远超预期的破坏力。

| 层级 | 角色 | 做了什么 | 错在哪里 |
|------|------|---------|---------|
| 训练代码 | **触发者** | 配错 NCCL 环境变量 | 配置错误，但配置错误的破坏半径不应这么大 |
| PyTorch | **放大器** | 超时后用 SIGABRT 直接杀进程 | 跳过所有 CUDA 清理，是导火索 |
| NVIDIA 驱动 550.163.01 | **根本原因** | 未能在进程退出时清理 GPU context | 进程已死，驱动应收缴所有资源而未做 |
| GSP-RM 禁用 | **加重因素** | 禁用 GPU 自管理 firmware | 失去 firmware 级状态重置能力 |
| Magnus/容器 | **暴露者** | GPU 隔离天生弱，全节点共享 nvidia.ko | 不是 Magnus 特有，是行业级限制 |

---

## 逐层分析

### 第一层：训练代码 — NCCL 配置错误（触发条件）

```bash
export NCCL_P2P_LEVEL=PXB      # 强制 PCIe Bridge P2P
export NCCL_ALGO=Tree          # Tree 算法
```

`PXB` 强制 NCCL 使用 PCIe Peer-to-Peer 通信，要求 GPU 之间通过 PCIe bridge 直连。但该节点的 ACS/IOMMU 阻止了这种直连，导致首次 FSDP ALLGATHER（5GB × 5 rank）完全卡死。

**这是配置错误，但问题的关键不在这里。** 一个网络程序配错了 IP 地址不应该让网卡永久故障；一个文件系统 mount 错了路径不应该让磁盘损坏。配置错误应该是可恢复的——进程退出，资源释放，下个任务正常开始。

### 第二层：PyTorch — SIGABRT 暴力退出（放大器）

NCCL watchdog 在 600 秒超时后，PyTorch 的 `ProcessGroupNCCL.cpp` 选择用信号 `SIGABRT (-6)` 直接杀死所有进程。

```
ProcessGroupNCCL.cpp → 检测到 NCCL 长时间无响应
  → killAllProcesses()
    → 向进程组所有成员发送 SIGABRT
```

SIGABRT 的特殊性在于：
- 不是 Python 异常（无法被 `except` 捕获）
- 不是正常的 `exit()` 调用（`atexit` 回调不会执行）
- 不经过 C++ 栈展开（析构函数不执行）
- **CUDA context 不会被正常销毁**

对比 17:06 那次正常 OOM：

```
17:06  OOM → Python torch.OutOfMemoryError → except 捕获 → 栈展开 → CUDA context 销毁 → GPU 正常
18:04  NCCL timeout → SIGABRT → 进程瞬间终止 → CUDA context 未销毁 → GPU 损坏
```

**PyTorch 选择 SIGABRT 作为 NCCL 超时的处理方式，是可以讨论的工程决策。** 但 SIGABRT 本身是合法的进程终止方式，操作系统和驱动都应当能正确处理。

### 第三层：NVIDIA 驱动 550.163.01 — 状态清理失败（**根本原因**）

**这是整个故障链的核心。** SIGABRT 杀进程的流程：

```
内核收到 SIGABRT
  → 内核清理进程资源
    → 关闭所有文件描述符（包括 /dev/nvidia0 到 /dev/nvidia4）
      → 调用 nvidia.ko 的 .release 回调
        → nvidia.ko 应该在此释放该进程的 GPU context
          → ✗ 但 550.163.01 没有正确释放
            → GPU context 残留在驱动内部状态表中
              → 后续所有 CUDA context 创建请求失败
```

**证据**：
- `nvidia-smi` 显示 `No running processes found` —— 内核确认无进程持有 GPU
- `nvidia-smi` 显示 GPU 显存 1MiB —— 驱动确认显存已清空
- 但 `torch.cuda.is_available()` 返回 False —— 新 CUDA context 创建失败
- 错误信息 `CUDA initialization: CUDA unknown error` —— 驱动内部状态不一致

**进程被内核杀死后，nvidia.ko 没有释放该进程的所有 GPU 资源。这是驱动的健壮性 bug。** 无论进程以什么方式退出（exit、SIGKILL、SIGABRT、SIGSEGV），内核驱动都应当在 `.release` / `task_struct` 清理路径中完整回收所有资源。

### 第四层：GSP-RM Firmware 禁用 — 失去自动恢复能力（加重因素）

该节点以 `NVreg_EnableGpuFirmware=0` 启动，即 GPU System Processor firmware 被禁用。

**GSP-RM 的角色**：GSP 是 GPU 上的独立处理器，运行 NVIDIA 提供的 firmware，负责 GPU 状态管理。当 GSP 启用时：

```
进程退出 → nvidia.ko 通知 GSP firmware
  → GSP 自主重置 GPU engine
    → 5-10 秒内 GPU 恢复可用
```

当 GSP 禁用时：

```
进程退出 → host driver 软件自行管理 GPU 状态
  → 依赖 nvidia.ko 的软件清理路径
    → 如果软件清理有 bug → GPU 状态残留
```

**GSP 是对抗此类问题的一条关键防线。** 禁用它意味着 GPU 状态管理完全依赖 host driver 软件路径，而这个路径在 550.163.01 中显然有缺陷。

检查 GSP 状态：

```bash
cat /proc/driver/nvidia/params | grep GpuFirmware
# EnableGpuFirmware: 0  ← 禁用状态

# 检查禁用原因
grep -r "EnableGpuFirmware" /etc/modprobe.d/ 2>/dev/null
grep "EnableGpuFirmware" /proc/cmdline 2>/dev/null
```

### 第五层：容器 GPU 隔离 — 行业级短板（暴露者）

管理员提出了一个非常合理的问题：

> "Magnus 提供的容器抽象应该是你咋搞都无所谓"

这个期望对于 CPU/内存/磁盘是正确的，但对于 GPU 不成立。原因在于 **GPU 容器隔离的本质**：

```
┌─────────────────────────────────────┐
│ 容器 A         │ 容器 B             │
│ /dev/nvidia*   │ /dev/nvidia*       │
│ libcuda.so     │ libcuda.so         │
│ (用户态)       │ (用户态)           │
└────────┬───────┴────────┬──────────┘
         │                │
    用户态│                │
  ───────┼────────────────┼──────────
    内核态│                │
         │    nvidia.ko    │
         │  (全节点共享!!) │
         │                 │
         │  GPU 状态表     │  ← 这里被污染了
         │  [0] [1] [2]    │
         │  [3] [4]        │
         └─────────────────┘
```

**对比其他资源的隔离**：

| 资源 | 内核隔离机制 | 容器 A 崩溃影响容器 B？ |
|------|------------|----------------------|
| CPU | cgroups v2, 独立的 task_struct | 否 |
| 内存 | cgroups v2, 独立的 mm_struct | 否 |
| 磁盘 | mount namespace, overlayfs | 否 |
| 网络 | network namespace | 否 |
| **GPU** | **无。所有容器共享 nvidia.ko 内部状态** | **是 ⚠️** |

NVIDIA GPU 没有类似 cgroups 的内核级资源隔离。`/dev/nvidia*` 只是设备节点——谁持有它谁就能与 `nvidia.ko` 通信。但 **`nvidia.ko` 内部的 GPU 状态表是全节点全局的**。一个进程的异常残留会阻塞该 GPU 上所有后续进程。

**这不是 Magnus 的问题。** 所有使用 NVIDIA GPU 的容器平台——Kubernetes + GPU Operator、Docker Compose + `--gpus`、Slurm + enroot/pyxis——都有完全相同的脆弱性。这是 NVIDIA 驱动架构的设计限制，容器平台无法在用户态解决。

## 责任比例（主观评估）

```
训练代码 NCCL 配置      ████░░░░░░  20%  触发条件
PyTorch SIGABRT 机制    ███░░░░░░░  15%  暴力退出
nvidia.ko 550.163.01    ████████░░  40%  根本原因：未清理异常退出进程的状态
GSP-RM 禁用             ███░░░░░░░  15%  失去自动恢复能力
容器 GPU 隔离弱         ██░░░░░░░░  10%  行业限制，非可控因素
```

**核心结论**：如果 nvidia.ko 在进程退出时正确清理了 GPU context（这是内核驱动的职责），SIGABRT 不会造成任何持久影响，配置错误只是一次失败的训练而已。

## 为什么同样的问题会在其他场景复现

GPU 损坏的触发条件远不止 NCCL 超时：

| 场景 | 触发信号 | 后果 |
|------|---------|------|
| NCCL 超时 | SIGABRT | 已知 |
| 容器 OOM killer | SIGKILL | **同样可能** |
| 用户 Ctrl+C 强制终止 | SIGHUP | 低概率 |
| Python segfault（c扩展 bug） | SIGSEGV | **同样可能** |
| 平台 job 超时强杀 | SIGTERM/SIGKILL | **同样可能** |
| CUDA kernel 超时（TDR） | 驱动级 GPU reset | 通常能恢复，但不保证 |

**只要异常退出 + GSP 禁用 + 550.163.01 这三个条件同时成立，GPU 就有损坏风险。** 这意味着同样的问题在节点上其他用户的其他任务中完全可能发生。

## 建议

### 对管理员（立即）

1. **`nvidia-smi -r`** 重置 GPU，几秒钟
2. 验证：逐卡 CUDA tensor 分配测试

### 对管理员（中期）

3. **排查 GSP-RM 禁用原因**：为什么设置 `NVreg_EnableGpuFirmware=0`？是否有已知兼容性问题需要 GSP 禁用？如果只是因为历史原因或无明确理由，建议移除该参数。GSP 启用后，GPU 状态恢复速度从 20-30s 降至 5-10s，且对异常退出的容错性显著提升。

### 对 Magnus 平台（长期）

4. **Job 完成后 GPU 健康检查**：在新 job 启动前用逐卡 CUDA tensor 分配验证 GPU 可用性。检测到损坏时：
   - 自动通知管理员
   - 如果平台有权限执行 `nvidia-smi -r`（需 root/SUID），自动复位
5. **考虑 GPU 亲和性**：如果节点上有 5+ 张 GPU，可以将异常 job 的 GPU 隔离，其他 job 使用剩余 GPU
6. **监控 `CUDA unknown error`** 作为集群健康指标

### 对驱动/硬件厂商（长期）

7. NVIDIA 需要改进 `nvidia.ko` 在进程退出时的 GPU context 清理路径，确保任何进程终止方式（包括 SIGKILL、SIGABRT、SIGSEGV）都能完整回收 GPU 资源
8. 考虑提供 per-process GPU state sandboxing（类似 cgroups 之于 CPU/内存），这是 GPU 容器化的基础设施需求
